# 8.3.1 Programación a la defensiva

Enlace: [[Fundamentos de programación.pdf#page=220&selection=356,0,366,4|Fundamentos de programación, página 220]].

Básicamente, el programador no siempre puede confiar en que el cliente ingrese un número cuando se pide un número en vez de un "ierqwbpjnrb". A veces se suele omitir este tipo de excepciones, pues suele simplificar el desarrollo.

Aunque también hay otras formas de robustez, como la que impide que se saque más dinero del banco que el que se tiene, y se imprima un mensaje de advertencia y se vuelva a pedir la cantidad.

Otra opción podría ser la siguiente: se pide una serie de números a dividir unos con otros y no se introduce ninguno, lo que produciría un aborto al dividir por 0.

La programación a la defensiva se encarga de eso mismo, de hacer que los programas y subprogramas estén escritos de manera que, pese a forzar un fallo, el programa siga hacia adelante. Hay siempre 2 opciones:

- El resultado es correcto, y por ende los datos son admisibles.
- Hay un error, por lo que los datos no son admisibles.

Hay un problema con todo esto, cuanto más robusto es un programa, más deficiente se vuelve, por lo que si los tiempos de ejecución son importantes, es recomendable sacrificar robustez.

Por ejemplo, para calcular un factorial, es necesario saber de antemano si el número al que se le va a aplicar dicha función es mayor o igual a 0, porque de lo contrario, va a dar un resultado incorrecto:

```c
int Factorial(int n) {
  /*
    PRE: n >= 0
    POST: Factorial(n) = (n = 9 → 1|n x Factorial(n - 1))
  */
  int f;

  if (n < 0) {
    f = 0;
  } else {
    f = 1;

    for (int k = 2; k <= n; k++) {
      f = f * k;
    }
  }
  return f;
}
```

Aunque pueda parecer robusta, no lo es de forma total, pues si el usuario introduce un número lo suficientemente grande, entonces el programa falla debido al error "*int overflow*", y en este caso, bastaría que `n` fuese igual a 20.
# 8.3.2 Tratamiento de excepciones

Enlace: [[Fundamentos de programación.pdf#page=223&selection=174,0,187,4|Fundamentos de programación, página 223]].

Es importante tener las siguientes 2 cosas en cuenta:

- Detección de la situación de error.
- Corrección de dicho error.

La programación defensiva recomienda que la primera opción se realice dentro del subprograma, por lo que entonces, se invocará siempre de forma corregida.

Hay una forma llamada "modelo de terminación" que se encarga de hacer el clásico `try` y luego ejecutar un `except` o `catch` para aguantar el error, aunque esto queda fuera del temario. En C++ está la sentencia `throw` que ayuda con el manejo de excepciones. Si el flujo llega al apartado de `throw`, entonces el subprograma se detiene por excepción:

```c
int FactorialRobusto(int n) {
  int f = 1;

  if (n < 0) {
    throw 0;
  }
  for (int k = 2; k <= n; k++) {
    if (f > INT_MAX/k) {
      throw k;
    }
    f = f * k;
  }
  return f;
}
```

Esto sí es robustez, si se sabe cual es el valor entero máximo, se puede hacer que el código falle menos.

El `throw` puede romper la claridad del programa, por lo que normalmente se usa `try` y `cathc (e)` para manejar esto de las excepciones. Así se vería el código de antes con dichas sentencias:

```c
#include<stdio.h>
#include<limits.h>

int FactorialRobusto(int n) {
  int f = 1;

  if (n < 0) {
    throw 0;
  }
  for (int k = 2; k <= n; k++) {
    if (f > INT_MAX/k) {
      throw k;
    }
    f = f * k;
  }
  return f;
}

void EscribirFactorial(int num) {
  try {
    printf("%2d! vale: %10d\n", num, FactorialRobusto(num));
  }
  catch (int e) {
    printf("%2d excepcion: ", num);
    if (e == 0) {
      printf("Factorial de numero negativo\n");
    } else {
      printf("Superado el límite al evaluar %2d!\n", e)
    }
  }
}
```
