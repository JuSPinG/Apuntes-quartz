# Introducción

El DNS (_Domine Name System_) se encarga de resolver nombres (como www.google.com) a IP en los que uno pueda conectarse. También puede funcionar al revés, a través de una IP, conocer el nombre del _host_.

Hoy en día dependemos tantos de los servidores DNS, que si no son accesibles, entonces, será muy complicado navegar por internet. 

# Metodología

Los servidores DNS consisten, en realidad, en una gran base de datos que recibe nombres y devuelve IPs (normalmente, aunque se puede dar el caso contrario). Además, cuenta con un programa autónomo que registra nuevos nombres y elimina las duplicidades innecesarias (pues puede haber alguna necesaria). Antiguamente, este proceso se llevaba a cabo sin la intervención de un servidor externo, es decir, las rutas se guardaban en el _host_ local, pero debido a su ineficiencia, se externalizó el proceso.

Los protocolos usados son TCP, para la transferencia de información con otros servidores, y UDP, para resolver nombres rápidamente, ambos en el puerto 53.

Un DNS requiere de 3 partes:

1. Datos que describen los dominios.
	1. Un servidor DNS debe de poder almacenar muchos dominios.
	2. Los datos se guardan en bloques de Registros de Recursos (o RRs), y estos se almacenan dentro de Archivos de Zona.
	3. El formato de los Archivos de Zona están estandarizados, y es común para la mayoría de _softwares_ que interpreten dicho formato, por lo que se puede encontrar repetido en varios servidores.
2. El programa del servidor DNS realiza estas 3 funciones.
	1. Lee un archivo de configuración, que define las zonas de las que es responsable.
	2. Un archivo de configuración puede describir varios comportamientos.
	3. Responde a peticiones de _hosts_.
3. Un programa o biblioteca de resolución.
	1. Se encuentra en cada _host_ y permite resolver nombres en consultas a servidores DNS.
	2. El _resolver_ se cachea en el _host_ (`etc/resolv.conf` en Linux y `C:Winsows/System32/drivers/etc/hosts` en Windows) para evitar nuevas consultas repetitivas. Cuando envía una petición y el TTL caduca, vuelve a comunicarse con el DNS

# Mecanismos de resolución

De nombre a IP o de IP a nombre:

1. IPv4: `in-addr.arpa`, nació sin ser pensado en resolver su nombre inversamente, pero con el paso del tiempo, se volvió un requisito obligatorio. `in-addr.arpa` se usa para el mapeo inverso de direcciones IPv4.
2. IPv6: `ip6.arpa`, que se usa para el mapeo inverso de direcciones IPv6, aunque en la práctica ya no es necesario.

Estas IPs ven sus fragmentos (como los octetos en el caso de las IPv4) invertidos para hacer búsquedas jerárquicas, de más común a menos común. Es decir, pasamos de 127.0.0.53 a 53.0.0.127. Esto se hace porque así las búsquedas se hacen desde lo específico a lo general, lo que es útil para indexar el árbol de manera inversa.

![[Mapeado inverso en redes.png]]

Este método de resolución es útil para rastrear actividad maliciosa, o como método de autenticación en el correo electrónico (de IP a nombre y de nombre a IP).

A este tipo de registros se le llamaba PTR, pero hoy en día se denomina "mapeo inverso", y por cada RRs se crea un RRs inverso.

## Tipos de servidores

El autoritativo no almacena resoluciones en el caché, mientras que el _forwarder_ (servidor de reenvío) actúa como un repetidor cuya información la guarda en el caché, como si fuese un _resolver_ de _host_. A veces, el autoritativo puede pedir información a otros servidores autoritativos, pero entonces no es el autor de la información, por lo que la respuesta es no autoritativa.

Se genera una relación de maestro y esclavo, donde el servidor _forwarder_ es esclavo del autoritativo pues su información depende exclusivamente de él.

## Redes entre servidores

![[Proceso de consulta DNS.png]]

El proceso es el siguiente:

1. La estación de trabajo necesita acceder a una página web de la cual conoce su nombre.
2. Tras revisar su propio caché (_resolver_), no encuentra el nombre, por lo que intenta acceder a un servidor DNS mediante una petición **iterativa** (pide y se desentiende el proceso).
3. El servidor al que accede, autoritativo o no, mediante una petición **recursiva** (pide múltiples veces hasta que resuelve el nombre).
4. El servidor busca servidores desde lo general a lo específico, por lo que entra a un DNS raíz, no encuentra el dato, por lo que vuelve a preguntar.
5. En un servidor DNS encargado del `.com` no resuelve su petición, por lo que el servidor vuelve a preguntar.
6. Finalmente, el último servidor DNS le devuelve la IP del nombre pedido.
7. El servidor DNS la recibe y se la envía al _host_, pero la petición no es autoritativa porque el autor es otro DNS al que han preguntado.

# Dominio raíz y TLD

El dominio raíz es el punto, es como el directorio `/` o `C:` en Linux y Windows. Debajo de estos están los TLD (_Top Level Domains_), algunos de ellos son:

1. gTLDs (_generic Top Level Domains_): .com, .org, .edu...
2. ccTLDs (_country code Top Level Domains_): .es, .fr, .ai...
3. Nuevos gTLDs (2004): Patrocinados, como .gal, .jobs o .cat; o no patrocinados.
4. Política gTLDs (2011): Se pueden crear los que se quiera, siempre y cuando se pague lo suficiente.

Todo esto gestionado por ICANN, siendo suyo el dominio raíz (que en realidad son 13), siendo, por lo tanto autoritativo, aunque cede la autoridad a los países en el caso de ccTLD.

![[Ejemplo dominio raíz ICANN.png]]

Como se ve en la imagen, la jerarquía es la siguiente:

1. Dominio ráiz.
2. TLDs.
3. SLDs.
4. ...
5. Subdominios y el espacio de Internet.

Cuando se tiene un nombre completo, como "pc01.direccion.mired.net." (incluyendo el punto), entonces, se habla de un FQDN (_Fully Qualified Domain Name_); si no lleva punto final, entonces, se habla de un NFQDN. Luego, el estándar IDN (_Internationalized Domain Name_) permitió el uso de carácteres no ASCII en la ruta, incluyendo así la "ñ".

## Tipos de servidores

1. Servidores raíz.
	1. De ICANN.
	2. Son 13 en total.
	3. Reciben consultas que no se resuelven localmente.
	4. Uso de FQDN.
	5. Conocidos por todos los DNS públicos.
	6. Funcionan con _anycast_ (misma IP en varios servidores, por lo que la conexión desde el _host_ se produce al servidor más cercano).
	7. No soportan consultas recursivas, solo iterativas.
2. Servidor autoritativo.
	1. Posee información de una zona geográfica.
	2. Responde autoritativamente si puede.
	3. Posee un modo "solo autoritativo".
3. Servidor maestro (_Primary_ antiguamente).
	1. Tiene los datos (posee los Archivos de Zona).
	2. Puede haber varios maestros por zona.
	3. Sincronización entre maestros (si hay).
	4. Notifica cambios a servidores esclavos.
4. Servidor esclavo (_Secondary_ antiguamente).
	1. Obtiene los datos desde un servidor maestro.
	2. Responde como autorizado.
	3. Puede (y debe) haber varios esclavos por zona.
	4. Si no encuentra a su maestro, los registros (SOA) se eliminan.
	5. Se puede encontrar información extra, sobre todo de su configuración, aquí: [[1.4 Transferencias de Zona DNS#^48018b|Transferencias de Zona DNS]].
5. Servicio _resolver_.
	1. Coge datos de un servidor autorizado y los almacena en el caché hasta que el TTL expira.
	2. Si la respuesta que da proviene de un servidor externo, entonces, no será autoritativa.
6. Servidor reenviador.
	1. Mueve peticiones entre servidores.
	2. Almacena peticiones en su caché.
	3. Estas acciones suelen aumentar la velocidad de toda la red.
	4. Suele desactivar las consultas recursivas.
7. Servidor oculto.
	1. No se indexa por otros servidores.
	2. Se usa para proteger información interna.
	3. Si es externo, solo devuelve respuestas autoritativas.
	4. Puede llegar a no compartir información con servidores públicos.
	5. Crea una zona privada.

# Tipos de registros

Los datos deben de cumplir con el siguiente estándar:

1. Todo se guarda en Archivos de Zona.
2. Cada entrada posee 5 campos.
	1. Nombre del dominio.
	2. TTL.
	3. Clase.
	4. Tipo.
	5. Registro del dato.
3. Los registros de recursos (RRs) describen las características de una zona o dominio, se pueden encontrar en estos formatos.
	1. Formato texto (archivos de zona): _owner-name ttl class type type-specific-data_.
	2. Formato binario (consultas/respuestas): _name ttl class type rdlen rdata_.

## Registros principales

1. SOA (_Start of Authority_): primer registro de una zona. Define: ^72be42
    1. Servidor primario de la zona.
    2. Contacto administrativo (correo sin @).
    3. Número de serie (AAAAMMDDSS).
    4. Intervalos: Actualización, reintento, expiración.
    5. TTL por defect: Es esencial actualizar el número de serie cada vez que cambie cualquier registro de zona.
2. NS (_Name Server_): Define servidores de nombres autoritativos del dominio o subdominio.
3. A: Dirección IPv4 (32 bits).
4. AAAA: Dirección IPv6. Recomendado por la IETF.
5. CNAME: Alias que apunta al nombre canónico verdadero. Redirección válida solo para un RR en el owner-name.
6. MX: Identifica servidores de correo. Incluye preferencia y nombre de host. Definido en RFC 974.
7. PTR: Puntero que asocia una IP con un nombre de host (zonas inversas).
8. TXT: Texto libre. Usado para comentarios y configuraciones como SPF y DKIM.
    1. SPF (RFC 7208): debe definirse en registros TXT (no en SPF, ya obsoleto).
    2. DKIM: _Domain Keys Identified Mail_ (DKIM) es un método de autenticación de correo electrónico que ayuda a evitar que los spammers y otros elementos maliciosos se hagan pasar por un dominio legítimo.
