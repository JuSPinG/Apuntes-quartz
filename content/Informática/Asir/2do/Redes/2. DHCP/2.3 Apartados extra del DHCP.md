# Solicitud de parámetros de red

Cuando en el servidor de Kea especificamos unas opciones concretas (como `"valid-lifetime"`) que más tarde se aplicarán a los clientes, podemos cambiar esto nosotros como clientes, si así se especifica en ambos dispositivos. En el caso de `lease-time` es de la siguiente manera, tan solo es necesario especificarlo en nuestro archivo de interfaz:

```yaml
[Match]
Name=eth0

[Network]
DHCP=ipv4

[DHCPv4]
# Especifica el tiempo de concesión deseado. 
# La opción DHCP 51 (Lease Time) se solicita en segundos.
SendOption=51:<tiempo_en_segundos>
```

Esto es en el caso de `systemd-networkd`, y el de `netplan` es:

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    eth0:
      dhcp4: true
      dhcp4-overrides:
        send-options:
          - option: 51
            value: <tiempo_en_segundos>
```
# Actualización del DNS

Es una buena opción combinar Kea con Bind9, así, si una IP es concedida a un _host_, su nombre y su nueva dirección serán aunados por el DNS. De esta forma uno puede hacer `ping` al nuevo equipo con la seguridad de que su nombre será resuelto.

Para configurar esta compatibilidad, es necesario habilitar la opción `"enable-updates": true`, instalar "`kea-dhcp-ddns-server`", y editar al gusto el archivo `kea-dhcp-ddns.conf`.
# _Relay_ de DHCP

Un servidor DHCP central que reparte direcciones a equipos en diferentes redes se enfrenta a un problema fundamental: los mensajes `DHCPDISCOVER` y `DHCPREQUEST` se manejan mediante tramas _broadcast_, por lo que los rúters bloquean dicha inundación, impidiendo que los mensajes lleguen a puerto alguno. El  _DHCP Relay Agent_ se encarga de solucionar este problema. El _relay_ encapsula dicho mensaje _broadcast_ en una trama IP _unicast_ cuya dirección se corresponde con la del reenviador DHCP, y a la que se añade un campo `Relay agent IP address` (`giaddr`) cuyo valor es la IP del reenviador. Una vez que llega con este método la IP del nuevo _host_ de la red, el servidor DHCP coteja el _pool_ de direcciones y le envía una usando los mensajes típicos ([[2.1 Funcionamiento del DHCP#Tipos de mensaje]]). Esta comunicación se hace siempre desde el _relay_.
