# Fase 1: Ejercicios varios
## Ejercicio 1: Gestión de permisos en entornos multiusuario

Imagina que eres el administrador de un equipo de desarrollo con varios usuarios, y necesitas configurar los permisos de un proyecto compartido entre tres usuarios: `monon1`, `tronko2` y `birmingan3`. Cada uno debe tener permisos específicos para un directorio de proyecto, de acuerdo con su rol.

1. Crear un entorno simulado de usuarios y grupos.
	1. Crea los tres usuarios y un grupo común llamado `devEria2`:
		```sh
		sudo adduser monon1 && sudo adduser tronko2 && sudo adduser birmingan3
		sudo addgroup devEria2
		sudo usermod -aG devEria2 monon1
		sudo usermod -aG devEria2 tronko2
		sudo usermod -aG devEria2 birmingan3
		```
	2. Crea un directorio llamado `di_recto` para el proyecto y cambia el grupo propietario a `devEria2`.
		```sh
		mkdir di_recto
		sudo chown :devEria2 di_recto/
		```
2. Configuración de permisos básicos.
	1. Configura los permisos para que solo los usuarios del grupo `devEria2` puedan escribir en el directorio.
		```sh
		sudo chmod 020 di_recto/
		```
	2. Verifica mostrando los permisos del directorio:
		```sh
		$ ls -all | grep di_recto

			d----w----  2 marcos devEria2  4096 oct 13 14:29 di_recto
		```
3. Configuración de permisos avanzados
	1. `monon1` debe tener permisos completos (lectura, escritura, ejecución) en todo el proyecto. Cambia el propietario del directorio a `monon1`.
		```sh
		sudo chown monon1:devEria2 di_recto/
		```
	2. Los otros dos usuarios del grupo solo deben poder leer y ejecutar archivos, pero no modificarlos. Cambia los permisos de modo que el grupo `devEria2` solo tenga permisos de lectura y ejecución.
		```sh
		sudo chmod 750 di_recto/
		```

### Preguntas

- ¿Qué sucede si un usuario fuera del grupo `devEria2` intenta acceder al directorio?
	- Daría error por falta de permisos, pues el último "0" especificado en `chmod` indica que no hay ni un solo _bit_ dedicado a los permisos de los usuarios fuera del grupo, es decir, no pueden leer, escribir o ejecutar.
- ¿Qué sucede si `tronko2` intenta modificar un archivo dentro del directorio?
	- También daría error porque no tiene permisos para hacer eso. El número "5" en `chmod` indica el número binario "101", lo que a su vez significa que hay 2 _bits_ dedicados a los permisos, 2 de 3, siendo el _bit_ central en encargado de autorizar la escritura, por lo que no, el usuario `tronko2` no podría acceder.

## Ejercicio 2: Control de acceso con _Bit SGID_ en directorios

El equipo de desarrollo necesita colaborar en un subdirectorio dentro de `di_recto`. Queremos asegurarnos de que cualquier archivo creado en ese subdirectorio tenga automáticamente el mismo grupo propietario (`devEria2`), para facilitar la colaboración.

> [!attention]- Antes de abordar la tarea.
> Voy a hacer el resto de tareas desde `root`, para así no tener que darme permisos constantemente para acciones que normalmente no lo requerirían, como navegar dentro de `di_recto/`.

1. Crear un subdirectorio para colaboración.
	1. Crea un subdirectorio llamado `di_afano` dentro de `/di_recto`.
		```sh
		mkdir di_afano # Es mejor aplicar este comando más tarde para que se apliquen los permisos
		```
	2. Cambia el grupo propietario del subdirectorio a `devEria2`.
		```sh
		setfacl -R -m u::rwx,g::rx,o::- di_recto # Para este directorio y los siguientes
		```
2. Aplicar el _bit SGID_: Puede ser útil consultar [alguna página](https://deephacking.tech/permisos-sgid-suid-y-sticky-bit-linux/) debido a la novedad del concepto.
	1. Aplica el _bit SGID_ al subdirectorio `di_afano`, para que todos los archivos creados en él hereden el grupo propietario.
		```sh
		chmod g+s di_recto/
		```
	2. Verifica y muestra los permisos del subdirectorio.
		```sh
		$ ls -all
		
			total 12
			drwxr-s---  3 monon1 devEria2 4096 oct 14 10:50 .
			drwx------ 26 marcos marcos   4096 oct 14 10:33 ..
			drwxr-sr-x  2 root   devEria2 4096 oct 14 10:50 di_afano
		# Como he creado el directorio desde root, la propiedad me pertenece. Habrá que cambiar eso
		chown monon1 di_afano/
		```
1. Crear archivos de prueba.
	1. Cambia a `tronko2` y crea un archivo llamado `archivo_tronko2.txt` dentro del subdirectorio `di_afano`.
		```sh
		touch archivo_tronko2.txt
		```
	1. Verifica y muestra los permisos y el grupo propietario del archivo.
		```sh
		ls -all

			total 8
			drwxrwsr-x 2 monon1  devEria2 4096 oct 14 11:02 .
			drwxr-s--- 3 monon1  devEria2 4096 oct 14 11:01 ..
			-rw-rw-r-- 1 tronko2 devEria2    0 oct 14 11:02 archivo_tronko2.txt
		```
### Preguntas

- ¿Cuál es el grupo propietario del archivo creado por `tronko2`?
	- De `tronko2`.
- ¿Qué ventaja aporta el bit SGID en un entorno de colaboración?
	- Facilita que cada uno pueda interferir en los archivos del otro en un margen específico. Perfecto para la colaboración.

## Ejercicio 3: Gestión de archivos temporales con _sticky bit_

Se ha creado un directorio temporal compartido entre todos los usuarios del sistema. Necesitas asegurarte de que todos los usuarios puedan crear y modificar sus propios archivos, pero no puedan eliminar o modificar archivos de otros usuarios.

1. Crear un directorio temporal.
	1. Crea un directorio temporal llamado `tmp_rano` en `/tmp`.
		```sh
		mktemp -d

			/tmp/tmp.iSBzP0R2Xj
		```
	2. Cambia los permisos para que todos los usuarios puedan leer, escribir, y ejecutar en el directorio.
		```sh
		sudo chmod 777 .
		```
2. Aplicar el _sticky bit_.
	1. Aplica el _sticky bit_ para evitar que los usuarios eliminen archivos de otros usuarios.
		```sh
		sudo chmod 1777 .
		```
	2. Verifica los permisos del directorio.
		```sh
		ls -all
		
			total 0
			drwxrwxrwt  2 marcos marcos  40 oct 14 20:33 .
			drwxrwxrwt 14 root   root   340 oct 14 20:33 ..
		```
3. Crear archivos de prueba.
	1. Cambia a `monon1` y crea un archivo temporal.
		```sh
		sudo su monon1
		touch archivoMuyMonon
		```
	2. Cambia a `birmingan3` y verifica si se puede eliminar el archivo de `monon1`.
		```sh
		┌──(birmingan3㉿kali-Linux-VSCode)-[/tmp/tmp.iSBzP0R2Xj]
		└─$ rm archivoMuyMonon
		rm: ¿borrar el regular file 'archivoMuyMonon'  protegido contra escritura? (s/n) s
		rm: no se puede borrar 'archivoMuyMonon': Operación no permitida
		```

### Preguntas

- ¿Pudo `birmingan3` eliminar el archivo de `monon1`? ¿Por qué?
	- No puede porque se ha aplicado el _sticky bit_, y solo los propietarios pueden realizar cambios en sus archivos, incluyendo la acción de eliminar.
- ¿Cómo ayuda _sticky bit_ a mejorar la seguridad de los directorios compartidos?
	- Así, uno se asegura que «entre bomberos nos nos pisemos la manguera», tocando cosas que no se deben tocar.
