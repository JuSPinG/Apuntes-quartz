Hay 2 tipos de transferencias de zona: completa (AXFR) e incremental (IXFR).

# Zona de transferencia AXFR

Antiguamente, los servidores DNS esclavos recorrían servidores DNS maestros en busca de información a actualizar. Si en este sondeo, se encuentra un resultado más actualizado que el que puede cotejar localmente el servidor esclavo, entonces, hace una nueva copia. Se solicita una transferencia AXFR. Por este motivo, es necesario actualizar el número SOA ([[1.1 Servicio DNS#^72be42|Servicio DNS]]). Pero tiene un problema, el SOA es una referencia global del archivo, por lo que la transferencia de zona es siempre completa. Las operaciones se hacen en el puerto 53, la transferencia por TCP y la consulta por UDP.

# Zona de transferencia IXFR

Permite que el esclavo y el maestro solo se cambien los registros que han cambiado, haciendo así la transferencia mucho más eficiente. Este método no está soportado por todos los servidores, pero es un estándar para los archivos grandes.

# Política de notificación NOTIFY

Cada 12 horas, independientemente de si se registran cambios o no, el servidor esclavo le pide la información al maestro. Como esto es un poco lento para servidores dinámicos, el estándar RFC 1996 introdujo una función (_NOTIFY_), para forzar la actualización de los servidores esclavos rezagados. Cuando se envía dicha petición, los servidores esclavos cotejan el SOA, y si es distinto, entonces, actualizan su información de la zona, ya sea por AXFR o IXFR. Se puede configurar al servidor maestro para que este mensaje se envía automáticamente cada vez que algún archivo de zona halla sido modificado.

# Seguridad en las transferencias, con ACL y TSIG

Para las transferencias de zona, Bind9 usa Listas de Control de Acceso (ACLs), que permite una protección simple basado en IP. Aunque con suplantación IP esta medida se puede sortear, es mejor que nada.

Por otro lado, TSIG/TKEY mejoran este protocolo de transferencias, y el acceso se hace mediante una clave de autenticación. Y dicha medida, nuevamente, se puede eludir con ataques de fuerza bruta.

# Ejemplo de configuración del servidor esclavo

```json
// Configuración de zona esclava para example.com

zone "example.com" {
    // Especifica el tipo de zona como "slave" (esclava)
    type slave;

    // Lista de direcciones IP de los servidores maestros.
    // En este caso, solo el 10.0.0.1
    masters {
        10.0.0.1;
    };

    // La ruta y nombre del archivo donde BIND almacenará
    // una copia de la zona transferida. que no tiene por qué coincidir con lo real en vuestro servidor
    file "slave/db.example.com";
    // Mucho cuidado con elegir un directorio que esté protegido por el sistema
};
```
